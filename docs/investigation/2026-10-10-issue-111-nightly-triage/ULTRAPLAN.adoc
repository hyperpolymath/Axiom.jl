== Root-cause analysis

=== Why nightly fails

Julia nightly builds contain unreleased, potentially breaking changes to
internal APIs. Axiom.jl's test suite is substantial (841-line `runtests.jl`
+ 13 included test files covering tensors, layers, serving APIs, interop,
verification, Aqua, JET, and more). Any upstream change to:

* `LinearAlgebra` internals (used by `qr`, normalization, adjoint)
* `Zygote` adjoint plumbing (the package is a hard dep, pinned `0.6, 0.7`)
* `HTTP.jl` / `JSON.jl` compatibility surfaces
* Base Julia `ccall`/`Libdl` semantics (used by the Zig FFI and crypto shim)

can cause a nightly-only failure that is *not* a bug in Axiom.jl itself.

=== Why this is expected and normal

The Julia ecosystem's standard practice is:

1. *Required gates* run on Julia LTS (`1.10`) and stable (`1` / `1.11`).
2. *Nightly* runs are informational-only (`continue-on-error: true`) and
   exist to provide early warning of upcoming breakage.
3. Nightly breakage is *expected* during Julia's development cycle and is
   *not* treated as a defect in the downstream package until the breaking
   change lands in a stable release.

Axiom.jl's configuration follows this convention exactly. The real
compatibility gates are:

* `julia-compat` (ci.yml): Julia 1.10 + 1.11 × 3 OSes — *all green*
* `test` (julia-test.yml): Julia 1.10 + 1 (stable), crypto-enabled — *all green*

=== Why fixing nightly is not the right action now

1. Nightly breakage is *upstream noise*, not an Axiom.jl defect. Fixing it
   would mean chasing an unstable target that changes daily.
2. Any "fix" applied today may break again tomorrow when nightly changes.
3. The estate's REPO-STANDARD-MUST-INTEND-LIKE.adoc (§Performance, §MUST)
   requires regression protection against *stable baselines*, not moving
   nightly targets.
4. The ULTRAPLAN decision fork (Julia matrix) already settled this:
   "`1.10 LTS floor + `1` stable + nightly(non-blocking)`" — nightly is
   explicitly non-blocking by design.

== Recommended resolution: *Accept with documented exemption*

=== Determination

Both checks are **accepted with a documented exemption**.

The exemption is:

[quote]
Julia nightly checks are informational-only. They run with
`continue-on-error: true` and never block merges. Nightly breakage is
expected during Julia's development cycle and does not indicate an
Axiom.jl defect. The real compatibility gates are Julia 1.10 (LTS) and
Julia 1 (stable), which are required checks and must remain green.

=== What "accept" means under the standing rule

The standing rule (standards#994, AC1) requires one of three determinations:

* **Fix** — the check is green on `main`, and the fix is in the repo.
  ❌ Not applicable: nightly is an upstream moving target.
* **Retire** — the check is removed.
  ❌ Not appropriate: nightly provides early-warning value.
* **Accept with a documented exemption** — ✅ *This is the correct
  determination*. The exemption is written down (this document), and the
  check remains in place with `continue-on-error: true`.

=== What "accept" does NOT mean

Per AC5 (standards#994):

> No class is closed by adding `continue-on-error`, by demoting a failure
> to a warning, or by dropping the check from the required set without
> AC1's determination. Repair or retire; never mute.

The `continue-on-error: true` was already present from the workflow's
authoring — it is not being *added* to close this issue. The determination
is that this existing configuration is the correct design, and the
exemption documents *why*.

== Decision record

[cols="1,1,3"]
|===
|Question |Decision |Rationale

|Fix nightly?
|No
|Nightly is an upstream moving target; fixes would be ephemeral.

|Retire nightly checks?
|No
|They provide early-warning value for upcoming Julia releases.

|Accept with exemption?
|*Yes*
|The existing `continue-on-error: true` is the correct design per
 Julia ecosystem convention. The exemption documents why.

|Change `continue-on-error`?
|No
|It is already `true`; no change needed.

|Promote nightly to required?
|No
|This would block all merges during any nightly instability, which
 is unacceptable for a downstream package.

|Add nightly-specific skip logic?
|No
|Over-engineering. `continue-on-error: true` is the standard pattern.
|===

== Binding standards and constraints

This ulplan is mindful of and compliant with:

* *REPO-STANDARD-MUST-INTEND-LIKE.adoc* — §MUST Dependability: "No silent
  corruption"; §MUST Performance: "Baseline benchmarks for critical
  operations"; §CI Gates: "Build + unit/integration tests" on stable
  baselines. Nightly is not a stable baseline.
* *RSR_OUTLINE.adoc* (RSR Template Repository) — Required files and CI
  matrix conventions. Nightly is explicitly outside the RSR required-gate
  set.
* *ULTRAPLAN.adoc* (2026-07-01) — Decision fork item 6: "1.10 LTS floor +
  `1` stable + nightly(non-blocking)". This ulplan is consistent with that
  decision.
* *REGISTRY-READINESS.adoc* — Nightly failure is not listed as a
  registration blocker (the human-maintainer track is).
* *GOVERNANCE.adoc* — BDFL + Consensus model; this is a Standard-level
  decision (CI configuration), requiring two maintainer approval.
* *standards#994* — Cross-cutting governance reds; AC1 requires a
  determination per class, AC5 prohibits muting without determination.
  This document satisfies both.
